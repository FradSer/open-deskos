# Hosted Pi keeps full capability; the Personal Bot coordinates instead of implementing

## Status

Accepted. Revised after independent review to distinguish prompt instructions from enforced limits. Revised again following the operator's explicit approval of a coordination-only resident Personal Bot: the coordinator loses generic mutation tools, while Hosted Pi keeps one full-capability profile for voice and Console requests. The historical decisions below remain evidence rather than being rewritten as a single uninterrupted policy.

## Context

The managed coding task existed to serve the voice path. Its request arrives as a spoken utterance that speech recognition transcribes at a distance, so `src/task-agent.mjs` appended a policy that forbade commits, pushes, installation, deployment, release activation, and product-service restarts, "even if the task text asks for it". That policy is pinned by `integrations/personal-bot/features/managed-tasks.feature` and restated in `integrations/personal-bot/docs/MANAGED_TASKS.md`.

The policy is a system-prompt instruction, not an enforced limit. The host builds the session with the default built-in tools, no tool allowlist, and only `appendSystemPrompt`, and its own documentation says the harness is "not a filesystem sandbox" and that the prohibitions are "agent instructions, not an OS-level command firewall". Removing it changes the likelihood of a mutation, not the capability to make one.

The operator first chose the opposite of this decision (keep the guardrail, including for the voice path) and then reversed it when they asked for full control. The earlier rationale (a request that arrives as a distant spoken utterance deserves a narrower capability) stopped being the deciding factor. The reversal is recorded here rather than presented as a single coherent decision: the earlier answer was accepted, then superseded on the operator's instruction.

## Current revision

Three operator-approved revisions follow. Neither adopts a global second-confirmation requirement or a restricted voice-origin worker.

The first separates coordination from implementation: the resident Personal Bot coordinates and inspects; implementation is delegated to Hosted Pi, which retains its full capability. The second moves Open DeskOS onto Pi 0.99.2 and makes codemode the single model-facing tool for both resident coordinator profiles. Hosted Pi gains codemode alongside its full coding tool set. The third requires every active host CLI and resident SDK to use Pi 1.0.0. It preserves the prior boundaries; v1.0 guarded-tool discovery uses membership, not optional property reads, and auxiliary classifier/image execution stays disabled. Historic sealed rollback releases are not rewritten.

A transcript is the user's request, not blanket authorization for unrelated production operations. Available tools, authorization for this request, and an additional confirmation step are different facts. Project guidance and explicit operational authorization still apply.

### Codemode is the declared surface, not a boundary

- For the resident coordinator, `codemode` is the only tool the model is told it may call. Reviewed capabilities use `exposure: "codemode"`: they are registered, listed in the codemode description, and never declared to the model as individual tools. Activation comes from the `defaultTools` setting plus a denylist of generic mutation and shell entry points. A registration allowlist is deliberately not used, because naming a codemode-only tool there would declare it to the model.
- The reachable set is the registered tools. Removing generic `write`/`edit`/`bash`/`powershell` from registration is what removes the entry point, and a resumed conversation does not restore it. This is a tool-surface boundary, not a filesystem, network, credential or custom-capability sandbox: a reviewed capability module still executes with the service account's permissions, and codemode scripts reach only registered tools through the normal tool pipeline.
- The script sandbox has no Node, filesystem, network or timer access of its own, and auxiliary model access is disabled for both resident profiles, so a script cannot widen its own reach by classifying, spawning or scheduling.
- Independent calls inside a script run as the script awaits them; a failed call rejects inside the script while the surrounding script keeps its partial output. Completed side effects are not undone and never authorize an automatic retry, so a coordinator reports uncertain mutation outcomes with their durable identities as before.
- Declaration, description and accessibility are three different facts. Tools declare truthfulness annotations that are unverified hints, so nothing here is a permission system or an operation firewall.
- Both resident coordinator profiles and Hosted Pi run with the project settings scope untrusted, and the operator's agent directory is the only settings scope they read. This is a separate fact from the tool decision: the SDK's resource loader resolves package sources and can install a missing one, and its project trust defaults to true, so leaving a checkout trusted would let repository content name tools, extensions, skills, prompts or packages for a desk-resident service.

## Decision

- The resident coding coordinator exposes `read`, `grep`, `find` and `ls` through codemode, plus operator-reviewed system capabilities. Generic `write`, `edit`, `bash`, `powershell` and, for the personal profile, even the inspection built-ins are denied registration for the coordinator, including when its conversation resumes. This is a tool-entry boundary, not a filesystem, network, credential or custom-capability sandbox: reviewed capabilities and System lifecycle tools can still mutate installed Widgets/Apps under their existing authorization contracts.
- The personal profile keeps the same shape. Its DiDi confirmation gate and its exact-current-turn memory grant are host-enforced and continue to apply through nested calls, so codemode does not become a way around them.
- Source implementation, dependency changes, and command execution are delegated to an explicit configured target and project. An absent target is reported as unconfigured; the coordinator does not regain local mutation tools or invent a target as a fallback. It reports the launch receipt and returns rather than polling until a coding turn completes, keeping later spoken status, steering, and cancellation requests possible. It does not introduce autonomous background work.
- A **Hosted Pi** has the desk's Pi host capability: every tool that host exposes, including commits, pushes, dependency installation, deployment, release activation, and service restarts. Apart from the two host-owned factories named below it loads no extension, skill, or prompt template, so this is the host's tool set rather than everything a full Pi installation could do.
- The worker's own session adds exactly two host-owned extension factories: the SDK's `codemode`, and an extension that records host check metadata. Neither widens capability.
- The worker's former edit-and-test-only guardrail stays removed, regardless of who started the session or which machine attached. One Hosted Pi capability, one worker profile. The coordinator/worker separation is not a restricted voice-origin Hosted Pi.
- The rules that are not capability limits survive unchanged: truthful verification reporting, no replay of an interrupted task on restart, durable receipts, development-root admission, the host-wide concurrency cap, and no automatic retry of a mutation whose outcome is unknown.
- Hosted Pi replaces the managed coding task term and semantics; the reporting side of a Console and the voice path both reach the same worker capability.
- Candidate-bound checks are host-observed evidence, not model prose promoted to certification. A worker may run a check through a host tool that observes the process exit and samples the project's source before and after it. The source scope includes tracked content (including deletions), executable modes, symlink targets without following them, and nonignored untracked files. Ignored files, dependencies, external services, and the execution environment are outside that scope. Matching samples are not an immutable snapshot or proof that nothing changed during execution. Unreadable, unstable, or oversized scopes report unavailable.
- Check evidence travels in the existing persisted session tool results/history, not in mutation receipts. Request digests remain idempotency identities; they are not source candidates. `finished` remains a turn outcome, and `verification: not_run` remains the absence of an independent verifier. A zero process exit does not prove that the selected command is an adequate test.
- Engineering lessons may be recorded by defect category with their evidence and applicability. They are data for later review, never an authorization source or an automatic way to rewrite the agent's governing instructions. Personal memory keeps its existing explicit-user-command gate. This increment does not add an autonomous memory writer.

## Consequences

- The voice path still reaches the full worker capability. A mis-transcribed delegated utterance can request a commit, push, install, deployment, or service restart on a configured target. That accepted worker-capability risk is not removed by making the resident coordinator non-implementing. The revision removes direct implementation from the coordinator and distinguishes capability from request authorization; it does not claim to provide an operation firewall.
- Existing installations that depended on direct resident coding must configure a Hosted Pi target before they can implement a spoken coding request. Readings and system lifecycle tools retain their current paths. Long coding work no longer needs to run inside the resident coordinator turn; fixture coverage proves handoff behavior, not microphone/provider latency or device acceptance.
- Control Attribution covers Console-driven sessions only. A voice-started Hosted Pi has no Console, so nothing on the desk marks it as more or less authorized than work the operator asked for by voice.
- The policy text in `integrations/personal-bot/src/task-agent.mjs`, the "Managed tasks only edit and test" scenario in `integrations/personal-bot/features/managed-tasks.feature`, the assertions that pin that policy text in `integrations/personal-bot/tests/task-runner.test.mjs`, and `integrations/personal-bot/docs/MANAGED_TASKS.md`'s "Tasks are not interactive terminal windows and do not take over existing Pi sessions" statement are superseded and must be updated with the spec. The pinned scenario lists installation, commits, pushes, deployments, and service restarts while the policy text also prohibits release activation; the scenario and the instruction must be aligned when the instruction is removed.
- Removing the guardrail does not widen admission: a Hosted Pi still needs an operator-configured development root, Pi credentials, and the concurrency slot.
- Mitigations still not adopted: an origin-scoped worker policy, a per-session operator confirmation from the Console, or a global local confirmation on the desk. Adopting any of these later changes the authorization/interaction contract and requires its own explicit decision. Reusing the DiDi confirmation implementation would not make that change policy-neutral.

## Considered options

- **Two profiles**: a restricted voice-originated task and a full-capability Console session. Rejected here because it preserves exactly the distinction the operator rejected. It remains the first mitigation to reach for if the accepted risk proves unacceptable.
- **Origin-scoped policy with explicit per-session escalation.** Not adopted for the same reason: the operator asked for one capability rather than a graded one.
- **Delegation preference while keeping resident `write`/`edit`/`bash`.** Rejected in the current revision: it leaves long-running direct implementation reachable and makes separation depend only on a prompt. The operator instead selected removal of those tool entries.
- **Automatic verified status from model text or exit zero.** Rejected: these are claims or process observations, not independent validation of an exact source candidate and an adequate check.
- **Per-dispatch grant labels as enforcement.** Not adopted: recording a model-selected label does not constrain shell actions. Any future grant ledger must distinguish declared intent from actual enforceable tool/OS boundaries.
