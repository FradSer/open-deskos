用户判定旧实现「和不使用 OpenUI 一样」：渲染结果仍是 `advice + 平铺 chips + 按钮` 的固定形态。诊断确认三层压制：`HOST_RULES` 禁止散文/限制 Readings 至 3、唯一示例就是 Advice+chips；Jev 的 grounded/unsupported 问题把每个可见卡片字符串当事实断言，组合越丰富越难过 0.8；渲染器把 Badge/Chip/Reading/Metric 全压成 `makeChip`、Stack/Readings 压成同一 class，16 个原语只剩约 8 种 DOM 形状。

**当前设计（模型拥有结构，宿主拥有事实与权限）**：
- `src/openui-contract.mjs`：`OPENUI_EXAMPLES` 提供三份明显不同的通用组合；`HOST_RULES` 要求「Different topics deserve different compositions」「Compose the card freely」，不再禁止报告式 Heading/Text 或把卡片限成扁平 chip 列表；`Readings` 放宽到 1-8。
- `src/proactive-qualification.mjs`（新）：`createProactiveJudge` 主动关闭 Jev 分类器，用 resident 普通零工具模型只问**一个** usefulness 问题；不构造 Jev client、不发 grounded/unsupported 问题、不把卡片文本或 `uiText` 放进判定 state。intent routing 的 Jev 客户端保持不变。判定 receipt 仍是 `{model, probability, groundingProbability, threshold, trigger, judgedAt}`，`model` 为 `provider/model`，旧 checkpoint 仍可加载。
- `src/agent.mjs` 暴露 `judgeOrdinary`；`src/main.mjs` 的 watch judge 与 `agent.mjs` 生成会话内 `proactive_judge` 都改走 `createProactiveJudge`；`scripts/test-agent-path-live.mjs` 同步。
- `src/proactive-generation.mjs` 的 `validateCardText` / `validateGeneratedBatch`：拒绝整句复述 advice 的散文、重复 Reading/Metric 对、以及**任何可见数字**（advice、Heading、Text、Badge、标签、值、Option）没有已引用观测支撑；`canonicalNumber` 保留时间整体、归一化小数与分隔符。关掉 Jev 分类器后，宿主这里机械绑定事实是唯一真实性入口。
- `src/proactive-jev.mjs` 不再是 proactive 链路的判定入口（保留给其他引用/兼容）。
- 渲染器 `runtime/shell/src/renderer/core/openui-dom.js` + `personal-agent-status.css`：Badge 独立为 span、Metric 加 `data-emphasis`、Stack/Readings/Row 用声明式 `openui-*` class（保留 `personal-agent-preview-chips` 兼容几何）、Heading 加引导线；仍守单一 17px、一个卡片表面、无同心框、textContent、语义 `--odk-*`。
- **Footer 是产品特性**：`plugins/personal-agent.js` 的 `bindRecommendationFooters()` 用产品 `sessionLabel()` 把「会话来源 + Reply」追加到每条 recommendation 的 `.agent-message-body` 末尾，Reply 的 `replyTo` 仍指向真实 remote 消息。`personal-agent-status.css` 的 `.agent-recommendation .agent-recommendation-footer` 是样式单一所有者（共圆 `--agent-radius-card` 20px、单一 17px、间距 `--agent-gap-block`）。页面 CSP `style-src 'self'`，零 inline style；`agent-radius.cjs` 跨 4 主题守住这些断言，remote 消息保留自己的 control 半径。旧截图脚本的 DOM 搬运/inline style 方案已废弃。
- **左下来源留白（第一原则：水平对齐）**：icon、来源文字、Reply 三者必须保持同一条水平线（垂直中心对齐，实测 `centreSpread:0`）。文字小且垂直居中 → 下方视觉留白约 27–30px 比左方 16px 大。**正确做法是增大左 padding 去匹配，绝不是把文字压到底**：上一轮曾用 `align-items:flex-end` 把文字压到 16px，导致三者中心差 13px、不再平行，被用户纠正并撤销。落地为 `.agent-panel .agent-recommendation .agent-recommendation-footer .agent-session-open { padding-left: var(--agent-pad-card) }`（12px，图标左 28 ≈ 文字下 27），三者水平线不动、Reply 不动、44px 点击区保留。必须带 `.agent-panel` 前缀匹配 `home-desk.css:299` 的特异性。`agent-radius.cjs` 新增 `centreSpread/leftInset` 断言，两个负向对照都抓住（破坏水平线→spread 13 FAIL；去掉左 inset→FAIL）。用户随后要求「icon 和文字往下一点点」：在保持 Reply 不动、icon 与文字严格共线（`iconTextSpread:0`）的前提下，给来源按钮加 `transform: translateY(2px)` 做光学补偿（文字下距 27→25、`sourceNudge:2`）。transform 不改布局盒，44px 点击区/Reply/共圆全不动。`agent-radius.cjs` 把 `centreSpread` 拆成 `iconTextSpread`（≤1）和 `sourceNudge`（受控 1–3px）；负向对照三种回归都 FAIL（水平线破坏 / 去掉左 inset / 下沉 13px）。教训：先确认最基本的对齐不变量，再调间距；不要为了凑数值破坏对齐；微调优先用 transform 而非改 align-items。
- **Markdown / 无卡片状态 / 卡片间距（三点修复）**：① `advice`（`personal-agent-suggestions.js`）和 `message()`（`personal-agent.js`）原本用 `textContent`，`**加粗**` 原样显示；改走产品现成安全渲染器 `root.odkPersonalAgentReply.render()`（markdown-it `html:false`、链接转文本、图片转 alt、纯文本仍 textContent；index.html 里 markdown-it 113 → reply 117 → openui-dom 137 → suggestions 138，加载顺序就绪）。② 上面那条无卡片 remote 消息是 owner 输入的 `assistant_update`，**保持纯文字语义、不伪造生成卡片**；文字同样走安全 Markdown；`.agent-message-actions`（home-desk.css）硬编码 `gap/margin 8px` 改 `var(--agent-gap-block)`(10px)，与 recommendation footer 统一节奏。注：`.agent-message` 是 21px heading、`.agent-recommendation` 才是 17px，这是 `personal-agent-status.css` 注释写明的有意设计，未擅改（如用户要上面那条也 17px 需另行确认）。③ 卡片间距不均根因：`.agent-message-body p { margin:0 0 12px }`（特异性 0,1,1）盖过 `.openui-heading/.openui-text { margin:0 }`（0,1,0），Heading→Reading 变 22px 而非 10px；用 `.agent-recommendation .personal-agent-preview-card :is(.openui-heading,.openui-text){margin:0}` 清零；Divider 去掉自带 `margin-block:6px`，间距由卡片 gap 单一所有者提供；Stack 末尾悬空 Divider 用 `.openui-divider:last-child{display:none}` 隐藏（样式层处理，DOM 适配器仍忠实渲染每个原语）。gate：`agent-radius.cjs` 加 advice `<strong>` 真实 DOM 断言 + 两气泡 footer gap 一致；`agent-type-scale.cjs` 的 ui 树加 Divider 并断言所有相邻 gap==`--agent-gap-block`、divider margin==0、尾线隐藏；均有负向对照。
- **两种 footer 完全一致（用户「我刚刚调整了很多」后的纠正）**：用户指出「没有 OpenUI 参与生成的消息，整个按钮或下方 footer 也要和 OpenUI 一致」。根因：我把 footer 样式全 scoped 成 `.agent-recommendation .agent-recommendation-footer` 独占，导致 plain remote 消息 footer 仍是 14px / Reply 8px 圆角 / 无左内缩 / 无 2px 下沉，与 recommendation 的 17px / 20px / 12px / translateY(2px) 不一致。修法：两种 footer 都由 `sessionLabel()` 生成同构 DOM（`.agent-update-sources`），把规则作用域从 `.agent-recommendation .agent-recommendation-footer` **提升到共享的 `.agent-update-sources`**，四条规则一次覆盖两种消息。特异性坑：① `home-desk.css` 在 `personal-agent-status.css` **之后**加载，其 `.agent-panel .agent-message-session .agent-session-open{padding:0}`(0,3,0) 会盖掉同级选择器 → 用 `.agent-panel .agent-update-sources .agent-message-session .agent-session-open`(0,4,0) 才赢；② liquid-glass 主题 `html[data-theme] #personal-agent :is(button...):not(.agent-session-open){border-radius:control}`（含 id）给所有按钮 4px，而 recommendation Reply 之前是靠 `#personal-agent .agent-recommendation .personal-agent-proposals button` 顺带命中才有 16px（隐式耦合）→ 用 `html #personal-agent .agent-update-sources .agent-message-session .agent-session-reply`(1,4,0) 压过，两种 footer 共用。`agent-radius.cjs` 用一个 `metrics(article)` 对称量测两条 footer 的 10 个字段（gap/marginTop/replyRadius/replyFont/nameFont/openPaddingLeft/openTransform/touchTarget/iconLeft/centreSpread）逐字段相等；负向对照（缩回 `.agent-recommendation` 独占）FAIL `replyFont:14 vs 17`。`personal-agent.feature` 删掉过期的「remote 保留自己 control 半径」断言，改成「两种 footer 一致」场景。注意：气泡**正文** plain 21px / recommendation 17px 仍是有意区分，未改（用户要的是按钮/footer 一致）。

Why: 之前「修冗余」把系统收敛到 advice 唯一句子反而固化了固定表单；关闭 Jev 分类器本身不够，必须同时改判定问题、放开生成规则、让渲染器区分原语。Footer 反复「不共圆」的根因是样式没有所有者——产品从不把 footer 放进 recommendation，PASS 全来自临时截图脚本的 inline style；做成产品特性 + 单一 CSS 所有者 + 真实 gate 才闭环。How to apply: 改建议 UI 时同时核对 OPENUI_EXAMPLES、HOST_RULES、proactive-qualification 的问题措辞、宿主数值绑定、`bindRecommendationFooters`、`personal-agent-status.css` 的 scoped 规则、以及 Electron gate（agent-radius / agent-type-scale / agent-home）与 `personal-agent.feature` 的 Given/When/Then 场景。
